# P12.10 — Latência do dashboard e Lakebase como fonte de leitura

> [SPEC-007](../specs/007-react-geo-dashboard/spec.md) §2, §3 e §6 · tasks: [P12.10](../specs/007-react-geo-dashboard/tasks.md).
> Resultados **não** são preenchidos pelo agente: quem roda no workspace registra. O agente preparou os scripts e este roteiro; as tabelas abaixo estão vazias de propósito.

## Pergunta

O critério da SPEC-007 §6 é p95 < 3 s para renderizar os municípios de uma UF com o cache de API frio. Onde está o tempo (warehouse, consulta, geometria) e o Lakebase vence as alternativas mais baratas sem ferir o princípio 1 (uma definição por métrica)?

## Roteiro (mantenedor, no `dev`, perfil `andrevidal`)

Variáveis comuns:

```bash
export DATABRICKS_CONFIG_PROFILE=andrevidal ATLAS_CATALOG=atlas_dev \
  DATABRICKS_HOST=https://<workspace> DATABRICKS_WAREHOUSE_ID=<id>
```

### 1. Latência por endpoint (o app sobe em processo; sem deploy)

1. Pare o warehouse (`databricks warehouses stop <id> --profile andrevidal`) e espere `STOPPED`.
2. `uv run python scripts/spike_dashboard_latency.py endpoints --label warehouse-frio --repeat 20`
3. Logo em seguida, com o warehouse aquecido: `... --label warehouse-quente`
4. Cole a saída (tabelas Markdown) na seção "Resultados".

Como ler: "cache frio" é a 1ª chamada de um app novo; "cache quente" são as 20 seguintes (devem ser de microssegundos a poucos ms). A execução `warehouse-frio` mede, na 1ª linha, o tempo de acordar o warehouse; as demais já pegam o warehouse aquecido por ela. A rede entre o navegador e o App não entra (vem na P12.8).

### 2. Alternativas mais baratas (antes do Lakebase)

| Alternativa | Como é medida |
|---|---|
| Aquecer o cache na subida, com atualização em segundo plano | Tabela "aquecer o cache": tempo de todas as consultas da tela em sequência e em 4 threads |
| Consultas do mapa agrupadas | Mesma tabela: o paralelo mostra o ganho de agrupar |
| Agregado pré-calculado derivado de `mv_recharges`, lido pelo warehouse | `uv run python scripts/spike_dashboard_latency.py aggregate --month 2026-10` cria `semantic.spike_map_agg` só com `MEASURE()` e compara a leitura de UFs com a consulta direta à metric view (confere também que os valores são iguais) |

### 3. Synced table do Lakebase (cria recursos reais: só rode se as etapas 1 e 2 não bastarem ou se quiser o dado para o ADR)

A tabela de origem é `atlas_dev.semantic.spike_map_agg` (etapa 2; `row_key` é a chave primária).

1. **Cota e projeto.** `databricks postgres list-projects --profile andrevidal`; se não houver projeto, `databricks postgres create-project atlas-spike --json '{"spec": {"display_name": "atlas-spike"}}' --profile andrevidal`. Anote se a criação foi aceita (cota).
2. **Pipelines antes.** Em Jobs & Pipelines, anote quantos pipelines estão ativos (`atlas_medallion` e qualquer outro).
3. **Synced table (SNAPSHOT):**

   ```bash
   databricks postgres create-synced-table atlas_dev.semantic.spike_map_agg_synced \
     --json '{"spec": {"source_table_full_name": "atlas_dev.semantic.spike_map_agg",
       "primary_key_columns": ["row_key"], "scheduling_policy": "SNAPSHOT",
       "branch": "projects/atlas-spike/branches/production",
       "postgres_database": "databricks_postgres",
       "create_database_objects_if_missing": true}}' --profile andrevidal
   ```

   Anote o erro exato, se houver. Se a sync criar um pipeline gerenciado, confira o **conflito com o limite de 1 pipeline ativo**: o `atlas_medallion` continua rodando? A sync falha por cota? Rode o `atlas_daily` depois para ver.
4. **Status:** `databricks postgres get-synced-table "synced_tables/atlas_dev.semantic.spike_map_agg_synced" --profile andrevidal` até `ONLINE`.
5. **Latência de leitura:**

   ```bash
   uv run --with "psycopg[binary]" python scripts/spike_lakebase_read.py --profile andrevidal \
     --endpoint projects/atlas-spike/branches/production/endpoints/primary \
     --user <papel do Postgres> --table semantic.spike_map_agg_synced --month 2026-10
   ```
6. **Limpeza:** `databricks postgres delete-synced-table "synced_tables/atlas_dev.semantic.spike_map_agg_synced" --profile andrevidal`; depois `DROP TABLE semantic.spike_map_agg_synced` no Postgres; `uv run python scripts/spike_dashboard_latency.py drop`; e `delete-project` só se o projeto foi criado para o spike e você autorizar.

### 4. Princípio 1

O Postgres não executa `MEASURE()`. O agregado da etapa 2 é montado só com `MEASURE()` de `mv_recharges` (um teste em `tests/test_spike_dashboard_latency.py` garante que nenhuma tabela `gold`, `silver`, `bronze` ou `commission` entra) e mora em `semantic`. Se o Lakebase for adotado, é essa tabela derivada que sincroniza, e uma definição nova de métrica passa a exigir regenerar o agregado.
